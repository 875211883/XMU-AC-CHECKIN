# 教学文档：XMU 畅课自动签到是怎么跑起来的

这份文档写给两类人：

- **使用者**：想搞清楚界面上每个按钮干什么、定时怎么配、出错去哪看；
- **二次开发者**：想读懂签到流程、门控设计、GPS 定位数学，然后自己改。

代码不长（`auto_checkin.py` 约 1100 行 + `control_panel.py` 约 1000 行 + `app.py` 约 800 行），
建议按本文顺序对照源码看一遍。

---

## 0. 全景：一次签到从启动到结束

```
你点「启动 / 重启」
        │
        ▼
 control_panel.start()  ── 注入 creds.env 凭据，后台拉起签到子进程（GUI 子系统，无黑窗）
        │
        ▼
 auto_checkin.main()  ── 看门狗循环：main_loop() 崩了就 5s/60s 后重启，10 分钟内超 10 次才放弃
        │
        ▼
 do_login()            ── ① 先试本地 Cookie 快照 → GET /api/profile 验证
                        ② 失效才走 xmulogin CAS 重新登录，并回写快照
        │
        ▼
 get_courses()         ── POST /api/my-courses（只要 id/name/display_name）
        │
        ▼
 每 15 秒一轮轮询（INTERVAL）
   └─ 按 course_filter.json 跳过没勾选的课
        └─ GET /api/course/{cid}/student/{sid}/rollcalls   ← 本人状态在这里（absent / on_call_fine）
             └─ 过滤：已结束的点名 / 已经签上的 / 不支持的 QR
                  └─ 【门控】checkin_gate()   ← 等班里先签的人 >25% 或 >20 人
                       └─ 数字：取码 → PUT answer_number_rollcall
                       └─ GPS ：探针测距 → 三角定位 → PUT answer  → 回查名单确认
                            └─ 成功：写 checkin_record.json + 事件流 [OK]
```

关键设计原则：**只做"服务端确实记我签上了"的操作**。所以 GPS 会回查名单，
课程列表的 `status` 才是"我签没签上"的唯一口径。

## 1. 登录与凭据

文件：`auto_checkin.py` → `do_login()` / `_load_cookies()` / `_save_cookies()`

1. **凭据来源优先级**：环境变量 `STUDENT_ID`/`PASSWORD` > `creds.env` > 交互输入（输入后回写文件）。
2. **会话复用**：把整个 cookie jar（含 domain/path/secure/rest）序列化到 `auto_checkin_session.json`。
3. **两个曾经踩过的坑**（都在代码注释里）：
   - **不要相信快照里的 expires**：服务端会滑动续期，磁盘上的过期时间停在保存那一刻，
     重新载入时客户端会提前丢弃 cookie → 401。所以载入时统一 `expires=None`，
     到底有没有效由 `GET /api/profile` 说了算。
   - **强制直连**：`requests.Session` 被替换成 `_NoProxySession`（`trust_env=False`），
     否则残留的失效系统代理（如指向已关闭的 127.0.0.1:5301）会把所有请求拦成 ProxyError。
     `xmulogin` 内部也 new 了 Session，所以替换的是**类**而不是实例。

## 2. 点名数据模型：两个 status 千万别混

这是整个项目最容易写错的地方，上游就因此把"已签上"误判成"失败"。

| 接口 | 字段 | 含义 |
|---|---|---|
| `GET /api/course/{cid}/student/{sid}/rollcalls` | `status` | **本人在这次点名里的状态**：`absent` = 没签，`on_call_fine` = 签上了 |
| 同上 | `rollcall_status` | **点名本身的状态**：`finished` / `in_progress` … |
| 同上 | `is_expired` | 不可靠！实测已结束的点名它仍然返回 `false` |
| `GET /api/rollcall/{rid}/student_rollcalls` | 顶层 `status` | **点名本身的状态**（in_progress / finished） |
| 同上 | `student_rollcalls[]` | 名单，每条里的 `rollcall_status == on_call_fine` 才算"这个人签上了" |
| 同上 | `number_code` | 数字码。**2026-10-10 起恒为 null**（服务端不再下发） |
| 同上 | `end_time` | 结束时间；课程列表那条恒为 null，只能从详情取 |

由此推出几个必须遵守的规则（代码里都有注释）：

- 判"要不要继续处理"看**本人 status**（课程列表），不能看详情顶层 status；
- 判"我到底签上没有"看**名单里本人那条**的 `rollcall_status`；
- 判"点名结束了没"要综合 `rollcall_status`（列表）、详情 `status`、`is_expired`，
  再加一个"点名时间过去太久"的兜底 —— 否则课程列表会长期挂着昨天的点名，
  让程序每 15 秒重试一次、取不到码就刷屏（这就是"界面里永远只有某一门课"的根因）。

## 3. 签到门控（本项目最有价值的改造）

### 3.1 为什么需要

无脑"发现即签"会变成**每次都是全班第一个签**，太显眼。门控的目标是：
**等班里足够多的人先签，我再签**，同时保证不因为等待而漏签。

### 3.2 判定规则

文件：`auto_checkin.py` → `checkin_gate()`，常量在文件开头：

```python
CHECKIN_GATE          = True   # 总开关
CHECKIN_RATIO         = 0.25   # 已签 > 全班 × 25%
CHECKIN_MIN_SIGNED    = 20     # 或 已签 > 20 人
CHECKIN_MAX_WAIT      = 120    # 等超过 120 秒 → 直接签
CHECKIN_MIN_REMAINING = 30     # 距结束不足 30 秒 → 直接签
```

判定顺序（**先算达标，再算保底**）：

```
signed, total = 名单里 rollcall_status == on_call_fine 的人数 / 名单总人数
若 名单读不到                      → 直接签（宁可早签也不漏签）
若 signed/total > 25% 或 signed>20 → 达标开签
若 已等待 ≥ 120s                   → 保底直接签
若 距 end_time ≤ 30s               → 保底直接签
否则                               → 继续等，下一轮再看
```

注意边界：阈值是**严格大于**，所以"恰好 16/64（=25%）"和"恰好 20 人"都还要等。

### 3.3 三个防呆设计

1. **自检**：`get_signed_stats()` 发现名单里本人已经是 `on_call_fine` 时，返回 `None`
   让调用方直接放行 —— 避免"已经签上了还在门控流程里排队"。
2. **门控失败不影响主流程**：查人数失败（网络抖动/字段变了）不会卡住签到，而是走保底直接签。
3. **事件不刷屏**：同一门课同一条消息首次立即记，之后每 4 次才记一条并标注「（第 N 次）」；
   `[WAIT]` 只在人数变化时记一次。

### 3.4 怎么验证门控真的有效

```powershell
python tests/test_gate.py          # 47 项离线用例：1/4 边界、20 人边界、超时、临近结束、空名单…
python tests/verify_gate_live.py   # 联网只读：拉真实名单，打印每门课"门控会怎么判"
```

`verify_gate_live.py` 会打印每门课的 `已签/总人数 = 比例 → 达标/未达标`，
以及 7 条边界用例的实测结果（**不会提交任何签到**，只发 GET）。
历史实战证据可以看 `checkin.log` 里的 `[GO] xxx 已签 51/60，达标开签` 这类行。

## 4. 数字签到流程

```
1) get_rollcall_detail(rid)                     → (number_code, 点名status, end_time)
2) number_code 为空（2026-10 之后的常态）
   → get_number_code_from_timetable(rid, cid, rollcall_time)
        GET /api/timetable_rollcalls?course_ids={cid}&rollcall_date={UTC 日期}
        ↑ rollcall_date 必须取点名时间的 **UTC 日期**；参数要写成重复参数，数组形式返回空
3) 两个通道都拿不到 → 记事件 "[!] xxx 签到码暂未获取，将重试"，并把当时的原始响应
   落盘到 code_missing_diag.json（每个 rid 只记一次，文件超过 256KB 只留最后 40 条）
4) 拿到码 → PUT /api/rollcall/{rid}/answer_number_rollcall
        body: {"deviceId": 随机 uuid, "numberCode": "0839"}
        200 → 记 [OK] 并写入 checkin_record.json
```

> 数字签到以 HTTP 200 为准；GPS 因为服务端"200 也可能在范围外"，会额外回查名单确认。

**QR 签到 (`qr_rollcall`) 不能自动签，但可以做半自动**，结论都有实测支撑：

- 课程列表里 `type='qr_rollcall'`、`source='qr'`（统计样本：38 条最近点名里 6 条是 QR）；
- 点名详情接口返回的**全部字段**是 `comment / end_time / external_api_key_id /
  is_number / is_radar / number_code / published_at / scored / section / status /
  title / type` —— **没有任何 token / 二维码内容**；`GET /api/rollcall/{id}/qr_code` → 404；
- 列表项里含 `qr/token/code/secret` 关键词的字段数为 **0**；
- 窗口极短：实测 `rollcall_time → end_time` 都是 **+10 分钟**。

也就是说 token 只存在于老师屏幕上那张二维码里，学生端 API 永远拿不到 —— 这正是
"人在现场"的证明方式。所以本项目的做法是**识别 + 提醒 + 半自动提交**：

### 4.1 识别（`_is_qr_rollcall` / `rollcall_label`）

按 `type` / `source` / `is_qr` 三个字段任一命中即判定为二维码点名，事件流写一条：

```
[QR] 线性代数(A) 是二维码点名，请用手机扫码（拿不到 token，脚本不会自动签）
```

同时把这条点名写进运行状态文件的 `qr_alert`（含课程名、截止时间、剩余秒数），
界面据此显示红色倒计时、响铃并置顶窗口（每条点名只提醒一次）。
旧版会把二维码点名当成"本人状态获取失败"，白重试 10 轮（约 2.5 分钟）后误报 `[GIVEUP]`，
这个 bug 已随本次改动修掉。

### 4.2 半自动提交（`answer_qr`）

接口（**无害探测得出**，对已结束的二维码点名 + 明显无效 token 测试）：

| 请求 | 返回 | 说明 |
|---|---|---|
| `PUT /api/rollcall/{id}/answer_qr_rollcall` | `400 {"error_code":"rollcall_already_closed"}` | **路径存在**，只是点名关了 |
| `PUT /api/rollcall/{id}/answer_qr_rollcall_typo` | `404 {"message":"未找到资源"}` | 对照组，确认上面不是"万物 400" |
| `POST` 同一路径 | `500` | 不支持 POST |
| `GET /api/rollcall/{id}/qr_code` | `404` | 服务端确实不下发 token |

参数名只在点名开着时才会校验，所以程序**一次性带上几个常见键**
（`qrCode / qr_code / code / token / qr_token / answer`），服务端取它需要的那个。
用户侧只要把二维码内容贴进来即可，两种形态都兼容：

```
https://lnt.xmu.edu.cn/api/rollcall/450660/answer_qr_rollcall?token=ABC123   → 取 token=ABC123
https://lnt.xmu.edu.cn/x/ABC123                                              → 取路径末段
ABC123                                                                       → 原样当 token
```

提交流程：**提交 → 回查名单里本人的 `rollcall_status` 是否变成 `on_call_fine`**
（与 GPS 一路做法一致），确认后才写 `checkin_record.json`。

用法：

```powershell
# 图形界面：二维码签到卡片 → 粘贴 → 「提交二维码」
# 命令行（自动找当前进行中的二维码点名）
XMU畅课签到.exe qr "<二维码内容或链接>"
```

> 合规提醒：这条路需要**你本人拿到二维码内容**（自己扫、或别人分享）。
> 拿别人分享的码替你签，本质上仍是代替现场扫码，风险自负。
> 如果二维码显示在**你自己电脑屏幕上**（线上课/投屏），也可以自己截屏后交给
> 任意二维码识别工具解码，再把文本粘进上面的入口。

## 5. GPS 签到：用两次"假打卡"反推坐标

点名开了 GPS 范围限制，服务端会告诉你"你距离目标太远"，并**返回距离数值**。
于是可以用两个已知坐标的探针，得到两个距离，再用两圆求交算出目标点。

### 5.1 流程（`answer_radar_auto`）

```
① 用探针坐标 A(24.3, 118.0)、B(24.6, 118.2) 各 PUT 一次 /api/rollcall/{rid}/answer
   - 任意一个 200 → 说明本次不限范围，已签上（回查名单确认后直接成功返回）
   - 否则从响应里取 distance → d1, d2
② 站心平面近似，把经纬度转成米制平面坐标
③ 两圆求交 → 一般得到两个交点（关于 AB 连线对称）
④ 两个候选点依次提交，每次都回查名单本人 rollcall_status，出现 on_call_fine 才算成功
```

### 5.2 数学

**站心平面近似**（小范围内足够准，`_latlon_to_xy`）：

```
x = R · (lon − lon₀) · cos(lat₀)
y = R · (lat − lat₀)          R = 6371000 m
```

**两圆求交**（`_circle_intersections`）：圆 1 圆心 P₁ 半径 d₁，圆 2 圆心 P₂ 半径 d₂，D = |P₂ − P₁|

```
a = (d₁² − d₂² + D²) / (2D)          交点到 P₁P₂ 连线垂足的距离
h = √(d₁² − a²)                       交点到连线的垂直距离
基点 M = P₁ + a·(P₂ − P₁)/D
交点 = M ± h · 垂直单位向量
```

**误差容忍**（`GPS_DISTANCE_TOLERANCE = 5 m`）：GPS 距离有舍入误差，两圆可能"差一点点相交"：

- `D > d₁ + d₂`（两圆分离）：差距 ≤ 5 m 时把两个半径各扩大 `gap/2 + 0.1`；
- `D < |d₁ − d₂|`（一圆套住另一圆）：差距 ≤ 5 m 时微调大圆半径使其内切。

**为什么要试两个交点**：两圆交点关于 AB 连线对称，只有一个是真的目标点，
所以不做几何猜测，直接两个都提交，用名单状态当裁判。

## 6. 界面教学（`app.py`）

界面是 Tk 单页 + 可滚动 Canvas，深/浅两套主题（右上角切换）。

| 区域 | 说明 |
|---|---|
| 顶部英雄区 | 呼吸灯 + 状态标题。**「未运行」= 你还没点启动**；「定时待机中」= 当前不在定时时段；「已手动停止」= 你点过停止 |
| 统计卡 | 今日签到 / 累计签到 / 监控课程（按勾选算）/ 外部启动次数 / 看门狗重启次数 / 实时尝试次数 |
| 启动 / 重启、停止 | **打开软件不会自动开始**，必须点「启动 / 重启」。点「停止」后不会被自动拉起 |
| 定时开关 | 每行 = 一个时段：启动时间、关闭时间、重复（每天/工作日/周末）。下面一行显示"当前是否在时段内 + 下次自动启动/停止"。「保存并注册」写入 Windows 任务计划 |
| 今日已签到 / 每门课查询次数 | 来自 `checkin_record.json` 与运行状态文件 |
| 监控课程 | 每门课一个复选框，勾选 = 抓取并自动签到；「全选 / 全不选 / 保存勾选」 |
| 账号设置 | 学号密码，保存到 `creds.env`（密码留空则保留原密码） |
| 实时控制台 | 最近事件流（`[NEW] [WAIT] [GO] [OK] [SKIP] [GIVEUP]`…） |

**数据从哪来**：界面每 3 秒刷新一次，`find_running()` 用纯 Win32 调用判断监控进程是否在跑，
其余全是读文件。**刷新循环里绝不启动子进程**（见第 8 节）。

## 7. 定时开关与自动启停

### 7.1 为什么要用 Windows 任务计划

进程被杀、电脑重启后，定时仍然要生效。所以「定时开关」不是 sleep 循环，
而是注册两个任务：`XMU-AC-AutoStart-N`（到点执行 `exe start`）、`XMU-AC-AutoStop-N`（`exe stop`）。

### 7.2 为什么不用 `schtasks /Create /SC DAILY`

它生成的默认 XML 是：

```xml
<DisallowStartIfOnBatteries>true</DisallowStartIfOnBatteries>
<StopIfGoingOnBatteries>true</StopIfGoingOnBatteries>
<StartWhenAvailable>false</StartWhenAvailable>
```

后果：笔记本一用电池就不触发；电脑在 06:00 关着/睡着，错过了就永远不补跑。
所以本项目**自己写 XML** 注册：

```xml
<DisallowStartIfOnBatteries>false</DisallowStartIfOnBatteries>
<StopIfGoingOnBatteries>false</StopIfGoingOnBatteries>
<StartWhenAvailable>true</StartWhenAvailable>      <!-- 错过时间在唤醒后补跑 -->
<MultipleInstancesPolicy>IgnoreNew</MultipleInstancesPolicy>
```

工作日/周末用 `<ScheduleByWeek><DaysOfWeek><Monday/>…</DaysOfWeek></ScheduleByWeek>`。

### 7.3 时段判定（纯 Python，可离线测）

`control_panel.py` 里有一组纯函数，界面和自动拉起都靠它们：

```python
schedule_window_active(slot, when)   # 支持跨天：22:00~02:00 前半夜+后半夜都算
schedule_active_now(when)            # 没配定时 → True（表示不限制）
schedule_next_change(when)           # 下一次"启动/停止"边界，用于界面提示
```

### 7.4 与「手动启停」的关系（容易踩的坑）

自动拉起（`_ensure_alive`）必须同时满足三个条件，否则会出现"点了停止 30 秒后自己又起来"：

1. 用户**点过**「启动 / 重启」（`_armed`）—— 打开软件不算；
2. 没点过「停止」（`_user_stopped`）；
3. **当前在定时时段内** —— 否则 23:30 的定时停止会被立刻顶回来。

若监控是定时任务/命令行启动的（软件观察到"已经在跑"），也会被保活。

## 8. 硬约束：GUI 里不能有任何"会开控制台窗口"的操作

### 8.1 现象

软件一启动，黑色 cmd 窗口每隔几秒闪一次；如果把 Windows Terminal 设为默认终端，
闪的还是 Windows Terminal 窗口。

### 8.2 原因

`XMU畅课签到.exe` 是 `console=False` 的 GUI 进程。它启动任何**没有隐藏控制台**的
子进程（`os.system("cls")`、不带 `CREATE_NO_WINDOW` 的 `subprocess`）时，
Windows 都会新建一个控制台窗口。而旧版 `find_running()` 每 3 秒就要跑一次
`tasklist` + `powershell Get-CimInstance` —— 于是每 3 秒闪一次。

### 8.3 现在的做法

| 位置 | 做法 |
|---|---|
| 进程探测 | 全部改成 `ctypes`：`CreateToolhelp32Snapshot` 枚举 + `OpenProcess/GetExitCodeProcess` 判存活 + 读 PEB 拿命令行（`NtQueryInformationProcess` + `ReadProcessMemory`） |
| 必须起子进程时 | `control_panel._run()` 统一加 `CREATE_NO_WINDOW`（`schtasks`/`taskkill` 等低频操作） |
| `os.system("chcp 65001")` | 改成隐藏控制台的 `subprocess.run(["cmd","/c","chcp 65001"])`，且只在真的挂着控制台时执行 |
| `os.system("cls")` | 先用 `GetConsoleWindow()` 判断有没有控制台窗口，没有就直接跳过 |
| 刷新循环 | 一个子进程都不起（纯文件读取 + Win32 调用） |

自检方法：任务管理器里盯 `tasklist.exe` / `powershell.exe` / `conhost.exe`，
新版本运行 20 秒内**新增数应为 0**。

## 9. 排障手册

### 9.1 日志与状态文件（都在 exe/项目同目录）

| 文件 | 内容 |
|---|---|
| `checkin.log` | 签到子进程的全部输出（行缓冲，超过 5MB 自动清空）。**排障先看它** |
| `auto_checkin_status.json` | 实时状态：重启次数、每门课查询次数、最近事件（界面读它） |
| `checkin_record.json` | 成功签到记录（时间/类型/课程/码） |
| `code_missing_diag.json` | 取码失败时落盘的原始响应（详情 + 课表接口），用于分析服务端口径变化 |
| `auto_checkin.pid` / `start_time.txt` | 监控进程 PID / 启动时间戳 |
| `launch_count.json` | 外部启动次数（手动/定时/重启都算） |

### 9.2 常见故障对照

| 现象 | 原因 / 处理 |
|---|---|
| 界面「未运行」 | 正常 —— 打开软件不会自动开始，点「启动 / 重启」 |
| 日志 `[登录] Cookie 已过期，重新登录...` | 正常自愈流程，会用 creds.env 重新登录 |
| `[配置] 读取 creds.env 失败` / 提示缺账号 | 检查 `creds.env` 是否有 `STUDENT_ID`、`PASSWORD` 两行 |
| `[!] xxx 签到码暂未获取，将重试` | 数字码两通道都没下发（服务端限制）；详情见 `code_missing_diag.json` |
| `[SKIP] 已跳过 N 个已结束的点名` | 正常：历史点名被清理，不再重试 |
| `[GIVEUP] xxx 已过 N 小时仍未下发签到码` | 超过 6 小时还没码，判定不会再下发 |
| `[WAIT] xxx 已签 a/b，未达标继续等` | 门控在等，正常 |
| `[QR] xxx 是二维码点名` | 正常：二维码点名脚本不会自动签，界面会响铃+倒计时提醒，可粘贴内容半自动提交 |
| 界面数字不刷新 | 看 `checkin.log` 是否还在滚动；若进程在但日志停很久，点「启动 / 重启」 |
| 定时到点没反应 | 任务计划程序里看 `XMU-AC-Auto*` 是否存在、上次运行结果；或点「保存并注册」重建 |
| 一闪一闪的黑窗 | 见第 8 节；确认没有别的工具（如某些厂商 watchdog）在起控制台程序 |

## 10. 打包成 exe

```powershell
pip install -r requirements.txt pyinstaller
python -m PyInstaller --noconfirm XMU畅课签到.spec
# 产物 dist\XMU畅课签到.exe（onefile + console=False）
```

踩过的坑（都写在 `control_panel.py` 注释里）：

1. **windowed 进程 `sys.stdout` 是 None**：`print()` 静默丢弃，子进程日志看不到。
   解决：签到子进程启动时把 `sys.stdout/sys.stderr` 指到行缓冲的 `checkin.log`。
2. **onefile 的环境变量污染**：`_PYI_*` 会让子 bootloader 误判层级，`PYTHONPATH` /
   `TCL_LIBRARY` / `TK_LIBRARY` 会污染模块与 Tk 搜索路径 → 启动子进程前剔除。
3. **`unicodedata.pyd`**：扩展模块有时抓不到，spec 里用 `sysconfig` 定位后显式加入
   （不要写死本机绝对路径）。
4. **`CREATE_NO_WINDOW` 与 `DETACHED_PROCESS` 不能同时用**。
